## 背景

平台要在不影响急诊、签核和审计的前提下持续升级。若直接替换数据库列、事件字段或 FHIR 表达，新旧服务会同时解释同一临床事实，导致重复、漏读或审计断链。LLM、规则、提示模板和模型依赖也会改变建议内容，因此“服务能启动”不等于临床兼容。

兼容性升级必须把代码、契约、数据和运行切换作为一个版本化变更。任何破坏性变更都要有消费者清单、迁移、观测和可执行回滚，而不是依赖现场临时修 SQL。

## 选项对比

| 方案 | 风险 | 回滚 | 适合场景 | 结论 |
|---|---:|---:|---|---|
| 大爆炸停机切换 | 高 | 差 | 无 | 禁止用于临床核心 |
| 原地改列/删旧字段 | 高 | 差 | 早期原型 | 不采用 |
| 向前/向后兼容双读双写 | 中 | 中 | 复杂迁移 | 仅在有明确期限时使用 |
| Expand–Migrate–Contract + 契约先行 | 可控 | 好 | 核心生产变更 | **采用** |
| 长期只增不删 | 中 | 好但债务高 | 未知消费者 | 必须有退休计划，不无限保留 |

## 决策

### 1. 版本与支持策略

- API 使用语义版本；事件信封包含 `schema_version`、`event_id`、`causal_id`、产生时间和兼容范围。
- 服务同时兼容当前与前一主版本，即 N/N-1；是否支持 N-2 以每个契约的消费者清册验证，不笼统承诺。
- FHIR R4 Profile、ValueSet、CodeSystem、Extension 和 FHIR 版本分别锁定；不得把“仍是 R4”误当成结构完全兼容。
- 数据库变更分三步：扩展（先加可空/新列）→ 回填与切换 → 收缩（观察期后删除旧结构）。
- 模型制品、提示、规则、Schema 和知识库各有不可变摘要，组合成完整决策版本；不能只记录模型名称。
- 同一临床重大版本可保留至少 14 天可回滚窗口和至少一个安全维护版本；实际支持期限由医院运维政策确认，标为 `[待验证]`。

### 2. 契约门禁

| 契约 | 自动门禁 | 人工门禁 |
|---|---|---|
| protobuf/OpenAPI | breaking diff=0；新增字段有默认语义 | API 负责人批准弃用 |
| FHIR | 官方 validator 100% 通过；Profile diff 报告 | 临床信息学审查 |
| 事件 | 旧消费者契约测试；未知字段容忍 | 规则/HITL 语义审查 |
| 数据库 | expand 阶段旧代码可运行；回填可重入 | 数据所有者签字 |
| 模型/提示 | 固定回归集、阴性对照、ECE 与安全阈值 | 临床/合规联合评审 |
| 安全制品 | 验签、SBOM、漏洞和许可证门禁 | 安全负责人批准 |

“breaking=0”只说明机器可读兼容，仍需判断临床语义。例如把枚举值改名即使类型未变，也可能是破坏性变更。

### 3. 发布与灰度

1. **准备**：冻结本次发布清单，生成迁移计划和回滚包，验证签名与依赖。
2. **扩展**：先部署向后兼容 schema/事件字段，复制或回填，不切换业务读取。
3. **小流量**：单院区/单非急诊能力运行 1%、10%、25%、50%，每档观察 SLO、语义差异和错误。
4. **切换**：达到门槛后切读新路径；双写必须使用同一幂等事件和事务水位。
5. **全量**：全院区运行完整观察期，观察 WORM 链、签核、FHIR 校验和数据库复制。
6. **收缩**：仅在支持窗口结束、所有消费者升级并出具证据后删除旧字段/API。

灰度比例按请求数还是风险加权由发布策略固定；高风险建议可按能力而非百分比分批。急诊核心默认不参与实验性模型灰度，除非满足 ADR-016 强制停用和本 ADR 临床回滚门禁。

### 4. 失败处理

- 出现未签核写入、审计断链、FHIR 校验失败、身份错误或数据不一致时立即停止晋级。
- 不兼容数据不自动猜测修复；隔离、保留原值并生成影响报告。
- 消费者在过渡期遇到未知字段必须保留并上报，不能删除后重发改变内容的事件。
- 兼容层有明确 owner 和删除日期；没有消费者的旧字段也不能无限积累 PHI。

## 可复算推导

### 双写容量

若新事件使每条平均增加 25%（该增幅为 `[待验证]` 的演算假设）：

```text
新增双写量 = 原写入量 × 25%
总瞬时写入 = 原写入量 × (1 + 25%) = 原写入量 × 1.25
```

若审计原计划 20 亿条/天且全量双写：

```text
旧写 = 2,000,000,000 条/天
新增写 = 2,000,000,000 × 25% = 500,000,000 条/天
总写 = 2,500,000,000 条/天
相对增幅 = 500,000,000 ÷ 2,000,000,000 = 25%
```

25% 为演算假设，实际增加按字段大小、索引和 WORM 批次测。验证方法是选 1% 观察者，测每条规范化字节、索引写放大、存储 IOPS、审计签名吞吐和 P99；不足时减少双写窗口或扩容，不能关闭审计。

### 14 天回滚窗口

```text
14 天 = 14 × 24 × 3,600 = 1,209,600 秒
```

窗口足够长不证明可回滚；数据迁移必须可逆或旧代码能读取扩展后的 schema。验证方法是在发布前从生产形态快照克隆到隔离环境，恢复前一版本并跑签核/FHIR/审计契约；若旧版本不兼容新数据，则按“两版本”支持政策延长或先撤销扩展。

### 灰度暴露量

按 5,000 名审核者、1% 灰度计算：

```text
灰度审核者数 = 5,000 × 1% = 50 人
```

50 人足以发现工程失败，但不足以证明罕见临床风险；临床安全还依赖合成/回顾性评测和强制停用阈值，不能把灰度人数当临床验证样本。

## 安全后果

- 旧版本若长期保留会带已知漏洞；安全补丁可以独立快轨，但必须保持契约兼容。
- 双写可能复制敏感数据到新表和备份，字段继承原数据分类、加密和访问控制。
- 模型灰度可能改变临床建议；每次建议绑定完整版本，异常时按原子版本组回滚。
- 回滚应用但不回滚已写数据可能造成旧代码误解新语义；因此迁移顺序和兼容矩阵是安全控制。
- FHIR 新旧编码混用可能改变含义；禁止静默映射，冲突进入人工术语确认。
- 外部制品须验签、扫描和锁定依赖来源；供应链不因升级窗口跳过门禁。

## 回滚方案

1. 每个发布包保存上一应用、契约、Profile、Schema、规则、模型和迁移的签名清单。
2. 先关闭新流量和新写入路径，等待在途请求到安全点；对未确认请求按 ADR-023 返回未知/查询。
3. 数据库回滚只执行经演练的反向脚本或让旧版本安全读取扩展结构；绝不删除新数据来“看起来回滚成功”。
4. 模型按完整版本组回滚，已产生建议保留原版本并进入临床复核/更正流程。
5. 事件发布者与消费者分阶段回滚，保证至少一个版本能读新格式；无法满足时进入只读或本院受限模式。
6. 回滚后对账 FHIR 资源、签核、审计链、消息水位和数据库记录；发现不一致即冻结相关写入并启动事件响应。
