# ADR-001：HITL 强制性的实现方式

## 文档头

| 项目 | 内容 |
|---|---|
| 状态 | 已接受（首轮规划） |
| 日期 | 2026-09-24 |
| 当前角色 | 医疗信息化首席架构师 / 平台安全负责人 |
| 本章产出 | 未签核建议不可进入病历或医嘱的三重强制机制 |
| 依赖的上游产出 | 主提示词 §3、§4.1、§4.2 ADR-001、§4.3 |

## 背景

Atlas 是临床协作、文书、审核与可审计层，不做自主诊断、自动处方，也不替代执业医师。AI 生成内容始终是“建议”；只有在具备有效人工签核证据后，才可形成可执行的临床写入意图。前端按钮禁用、提示词约束或单个 API 鉴权检查都可能因旁路调用、消息重放、并发状态覆盖或数据库直写而失效，因此 HITL 必须成为不可绕过的系统不变量。

本 ADR 约束的是所有会进入病历、医嘱、处方、护理任务或外部临床接口的建议型写入，不因 UI 入口不同而降低要求。

## 选项对比

| 方案 | 防线 | 优点 | 失效模式 | 结论 |
|---|---|---|---|---|
| A：仅前端校验 | 用户界面 | 实现快 | 直调 API、消息消费者或 SQL 可绕过 | 拒绝 |
| B：状态机 + 服务层 | 应用流程 | 能表达审批生命周期 | 持有合法数据库角色的错误程序仍可直写 | 拒绝 |
| C：状态机 + DB 约束 + 服务层三重强制 | 业务不变量、持久化不变量、接口不变量 | 任一层被绕过，其他层仍拒绝；可集中告警 | 迁移与运维更复杂，需专用数据库角色 | **采用** |

## 决策

### 1. 状态机强制

采用显式、封闭、版本化的 `SuggestionStateMachine`。下表是**写回资格投影**，用于数据库约束和 API 证明；架构中的 `DRAFT`、`EVIDENCE_READY`、`NEEDS_INFO`、`WRITEBACK_PENDING` 等是同一投影之前的细粒度工作流状态。抢救分支不映射到 `APPROVED` 或 `COMMITTED`，只能进入独立的紧急确认、事后复核和归档链。

投影状态为：

| 状态 | 含义 | 允许的下一状态 |
|---|---|---|
| `GENERATED` | AI/规则已生成建议，尚不可执行 | `PENDING_REVIEW`、`REVOKED`、`EXPIRED` |
| `PENDING_REVIEW` | 等待签核 | `APPROVED`、`REJECTED`、`REVOKED`、`EXPIRED` |
| `APPROVED` | 已完成所需人工签核，尚未形成写入意图 | `COMMITTED`、`REVOKED` |
| `REJECTED` | 人工拒绝 | `REGENERATED` |
| `REGENERATED` | 基于新证据重新生成，旧建议失效 | `GENERATED` |
| `EXPIRED` | 临床上下文或授权已失效 | 终态 |
| `REVOKED` | 撤回、停用模型或策略变化导致失效 | 终态 |
| `COMMITTED` | 已写入目标临床系统 | 终态 |

合法迁移为：`GENERATED→PENDING_REVIEW`、`PENDING_REVIEW→APPROVED|REJECTED|REVOKED|EXPIRED`、`APPROVED→COMMITTED|REVOKED`、`REJECTED→REGENERATED`、`REGENERATED→GENERATED`。任何未列出的迁移均返回拒绝码并产生安全审计事件；`COMMITTED` 不可原位撤销，只能追加 `REVOCATION` 事实并由目标系统执行受控冲正。抢救动作即使由人工签发，也必须保持 `EMERGENCY_PENDING_CONFIRMATION` 等独立状态，不能借此获得普通 `COMMITTED` 写回能力。

状态迁移必须原子校验：建议版本、临床上下文版本、规则版本、模型版本、患者身份、审核者执业授权、签核策略版本和过期时间。并发审核采用建议版本比较；旧版本请求失败，不能重复签核。

### 2. 数据库约束强制

采用“签核证明 + 不可变证书 + 外键”的数据库不变量：

1. `hitl_review` 保存每次审核事件；审核者、决定、时间、原因码、签名密钥标识、策略版本均不可变。
2. 仅当状态机事务内的受控存储过程验证 `PENDING_REVIEW` 后，才可向 `hitl_approval_certificate` 插入证书。证书至少包含 `advice_id`、`advice_version`、`decision=APPROVED`、`reviewer_id`、`approved_at`、`policy_version`、`nonce`，其主键为不可变值。
3. 所有临床写入表必须携带非空 `approval_certificate_id`，并以复合外键绑定到证书；证书另含 `advice_id` 与写入目标对象类型，应用写入时再次核对三者一致。
4. 数据库触发器拒绝以下情况：证书不存在、证书决定不是 `APPROVED`、建议状态不是 `APPROVED`、证书已过期、证书与目标对象/患者不一致。`hitl_approval_certificate` 禁止 `UPDATE` 与 `DELETE`，撤销和纠正只能追加事件。
5. AI 推理、规则引擎、消息消费和普通业务账号不拥有证书插入权或临床写入表权限；只有 `atlas-hitl` 的最小权限数据库角色可提交经状态机生成的证书及写入事务。
6. 任一约束被异常、迁移脚本或高权限账号绕过时，完整性监控必须立即告警、冻结该写入源并保留证据；不得提供“紧急跳过”开关。

抢救动作使用独立的 `EmergencyActionGrant` 与 `EmergencyWriteIntent`：证明绑定单一患者、建议版本、目标动作、理由码、授权人、有效期、策略版本和一次性 nonce；数据库只允许其产生 `EMERGENCY_RECORDED` 或 `EMERGENCY_UNKNOWN` 事实，不能插入普通 `approval_certificate`、不能迁移到 `APPROVED`/`COMMITTED`，不能被普通 `WriteIntent` 接受。目标回执未知时只允许对账，事后独立复核和受控更正追加新事件。该约束在目标数据库上的外键、唯一 nonce、不可变审计和最小权限行为为 `[待验证]`，验证方法是对普通证明、过期/重放/错患者/错动作/伪造状态五类攻击逐一注入，并检查数据库拒绝与审计事件。

目标数据库版本对所需外键、触发器及不可变权限的完整语义为 `[待验证]`。验证方法：在拟部署的 TiDB 具体版本和备选库上分别执行“缺证书、未批准证书、错患者、过期证书、更新证书、直写医嘱”六类集成用例，并检查事务回滚、权限拒绝和审计事件；逐项记录引擎行为与版本号。

### 3. 服务层强制

所有临床写入 API 只接受结构化 `ApprovalProof`，不得接受布尔字段 `approved=true`。证明由 `atlas-hitl` 在签核事务成功后签发，至少绑定建议及版本、审核者、患者、目标动作、风险等级、策略版本、有效窗口和随机数；有效期不得跨临床上下文版本。写服务必须：

- 在入口验证证明签名、时效、撤销列表及单次消费标识；
- 在同一数据库事务内重新读取建议锁定状态并验证目标患者/动作；
- 重新检查 `atlas-hitl` 写权限和双人复核策略；
- 消费证明、写临床记录与追加审计事件，随后将建议迁移到 `COMMITTED`；
- 对所有拒绝返回稳定错误码并记录 who/when/what/why，不因重试生成第二份临床记录。

模型服务、CDSS、LLM 文书服务和前端永远不持有写库角色。即使内部模块错误调用写 API，没有状态机签发的证明也会在服务层被拒绝。

### 4. 统一门禁与验证

| 门禁 | 通过条件 |
|---|---|
| 状态机穷举 | 每个非法迁移均被拒绝并审计 |
| DB 攻击集 | 缺证书、错关联、过期、未批准、重复使用等均失败 |
| 服务层契约 | 仅接受有效且未消费的 `ApprovalProof` |
| 重放/并发 | 同一 `nonce` 只能成功一次；旧建议版本不能提交 |
| 旁路监控 | 直写、权限异常和约束绕过触发 P1 告警 |

## 可复算推导

附件要求构造 100 条绕过路径并达到 100% 拒绝。可复算验收规模如下：若按 10 类绕过面、每类 10 条路径验收，则 `10 × 10 = 100` 条；通过率为 `100/100 = 100%`。测试用例清单、输入、服务调用、数据库快照和审计事件必须作为不可变证据归档。实际覆盖分类是否足以代表真实旁路为 `[待验证]`；验证方法是结合代码调用图、数据库权限矩阵、消息主题清单和威胁建模进行独立复核。

## 安全后果

| 后果 | 控制与残余风险 |
|---|---|
| 未签核内容进入临床系统 | 三重防线把风险降为目标为零；超级管理员仍可能破坏数据库，依赖职责分离、数据库审计和外部校验发现 |
| 审批凭据泄露 | 证明短时、单次、绑定患者与动作；签发密钥进入 Vault，使用独立工作负载身份 |
| 重复签核/重复执行 | 建议版本、幂等键和 `nonce` 联合防重；跨系统最终一致仍需补偿流程 |
| 紧急救治延误 | 抢救场景由 ADR-002 的受控破窗处理；该机制不放宽病历/处方红线的审计要求 |
| 状态机复杂度 | 用属性测试和可解释迁移表约束；发生缺陷时安全降级为“拒绝写入” |

## 回滚方案

1. 上线前采用向后兼容迁移：先部署状态机与证书表，再部署写服务，最后切换账号权限；旧应用在切换窗口只读。
2. 若新写路径异常，关闭新建议生成或写队列消费，不关闭签核校验；已签核未提交证明进入幂等补偿队列。
3. 若服务层缺陷，回滚至仍执行 DB 证书外键与触发器的保守版本；若 DB 迁移有缺陷，则停止相关写入、保留证据，从最近备份恢复审计元数据，核对所有证书链后重新放行。
4. 永不以数据库回滚删除签核事件；补偿记录必须引用原事件。回滚后连续执行 100 条绕过回归，全部拒绝才恢复流量。
