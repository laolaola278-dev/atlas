## 背景

排障需要 traceId、规则版本、延迟和状态码，却不需要姓名、证件号、完整病历或模型原始提示。Go 服务常见泄漏路径是 `fmt` 打印整个请求、错误包装携带响应体、URL 查询参数记录患者标识、OpenTelemetry baggage 携带整个对象，以及前端错误上报附带页面内容。采集端后统一清洗无法阻止明文在进程、磁盘和代理中短暂存在。

本 ADR 要求在产生日志的进程内先结构化、再按白名单输出。不可重采集的受保护审计事实进入独立加密审计库，不混入可搜索普通日志。20 亿条/天的审计事件与运行日志是不同数据产品，不能以“需要追踪”为由都写普通日志。

## 选项对比

| 方案 | 初始泄漏面 | 可证明性 | 排障能力 | 结论 |
|---|---:|---:|---:|---|
| 采集后用正则清洗 | 高 | 低 | 高 | 不采用为唯一防线 |
| 敏感字段黑名单 | 中 | 低 | 中 | 易被新字段绕过 |
| 结构化字段白名单 + 本地序列化时脱敏 | 低 | 高 | 高 | **采用** |
| 客户端加密后集中脱敏 | 客户端高 | 中 | 中 | 作为传输保护，不替代本地脱敏 |
| 原始日志全量加密后长期保存 | 中 | 低 | 高 | 最小化与访问风险过大，不采用 |

## 决策

### 1. 四类数据与去向

| 类别 | 示例 | 允许去向 | 禁止示例 |
|---|---|---|---|
| 运行日志 | 状态码、组件、耗时、规则版本、traceId | 院内日志平台 | 请求体、提示、完整响应 |
| 指标 | 延迟分位、错误率、队列深度 | 指标平台 | 患者标签、自由文本、稀有病小样本值 |
| 追踪 | span 名、span 属性、引用 ID | 追踪平台 | 病历段落、设备报文、访问令牌 |
| 审计 | who/when/what/why、对象引用、签名摘要 | 加密 WORM 审计库 | 混入普通日志后依赖以后再删 |

`traceId`、内部 `patient_ref`、设备内部引用可帮助关联，但必须先确认其不可在外部反查；所有导出日志都按数据出站规则执行。

### 2. 本地白名单

1. 每个模块定义结构化字段模式，只允许 `event_name`、`component`、`outcome`、`latency_ms`、状态码、错误分类、规则/模型/Schema 版本和受控引用。
2. 患者关联在日志中使用按租户隔离、不可逆的关联别名；需要稳定关联时使用独立密钥 HMAC，而非裸姓名、手机号或证件号的普通哈希。
3. HMAC 密钥与加密密钥分离，按用途和院区隔离；轮换时支持短时双键验证，不能用截断后的可枚举哈希代替。
4. 错误包装只传错误分类和内部事件 ID。HTTP 响应体、数据库错误中的参数、模型原始文本和设备原始报文不得自动进入 error string。
5. URL path 采用路由模板 `/patients/{patient_ref}/records/{record_ref}`，查询参数单独白名单；token、cookie、Authorization、Set-Cookie 一律禁止。
6. 调试采样在脱敏完成后进行，禁止先采原始对象再过滤。

### 3. 受控调试与例外

- 生产问题需要查看更多字段时，使用字段级 break-glass 调试开关，限定院区、对象、时长和工单号，默认不持久化。
- 临时捕获必须在业务停止后自动销毁并记录“创建/查看/销毁”审计；不能用“排障需要”绕过患者最小必要。
- 任何脱敏规则新增、删除或放宽均需隐私/安全评审；未知字段默认丢弃。
- 供应链日志和前端 source map 分开治理，source map 可能包含路径、符号和样例数据，不默认公开。

### 4. 检测门禁

CI 和运行期同时执行：

| 检测 | 规则 | 行为 |
|---|---|---|
| 标识符模式 | 姓名标签、手机号、证件号、病案号格式 | 命中即阻断或隔离 |
| 字典匹配 | 合成敏感词库、院内字段名 | 命中后分类为疑似 |
| 熵检测 | 长随机串、编码块、压缩内容 | 告警并路由安全复核 |
| 允许字段差异 | 新字段不在 schema | 拒绝上线 |
| 日志金丝雀 | 注入可识别的纯合成标记 | 验证采集端不会丢弃允许字段 |

熵检测只能作为信号，不能证明无 PHI；零告警不是合规证明。规则误报率、漏报率及适配中文数据的有效性为 `[待验证]`，验证方法是使用经批准的合成语料与隔离评估样本做标注集测试。

## 可复算推导

### 容量演算

假设每日 1,000,000 条普通运行日志、每条序列化后 2 KiB：

```text
日原始量 = 1,000,000 × 2 KiB = 2,000,000 KiB
         = 1.953125 GiB/天
30 天    = 58.59375 GiB
三副本   = 175.78125 GiB
30% 余量 = 175.78125 ÷ 0.70 = 251.116 GiB
```

这是规划演算，不包含 20 亿条/天 WORM 审计。1,000,000 条/天与 2 KiB/条均为假设，标为 `[待验证]`。验证方法是以实际日志事件类型采样 7 天，测 p50/p95/p99 大小与压缩率，并确认索引和副本开销。安全日志若 p99 超过预算，应减少字段，不应恢复原始内容。

### 关联开销

设 HMAC 输出 32 字节、10,000,000 条建议各记录 1 个患者关联：

```text
纯 HMAC 字段量 = 10,000,000 × 32 = 320,000,000 字节 = 320 MB
加 30% 余量 ≈ 320 ÷ 0.70 = 457.1 MB
```

仍需计入序列化、索引和编码，容量不是总表空间。验证方法为分别测 16/32 字节截断的碰撞与关联收益；截断降低空间，但必须证明在目标规模和用途下碰撞风险可接受。

### 审计量分离

```text
20 亿审计事件/天 ÷ 86,400 = 23,148.15 事件/秒
```

该负载不得原样进入普通日志。普通日志只记录批次 ID、根哈希和结果，详细事件留在受控 WORM；否则“日志平台”会同时承担高敏证据与高吞吐检索两种冲突职责。

## 安全后果

- 过度脱敏会降低根因分析能力；用受控事件 ID、版本和双向计数替代原文，而不是删除全部上下文。
- HMAC 若使用全局低熵密钥或可公开映射，仍可能被字典攻击；密钥、租户隔离和访问审计必须落实。
- 日志平台管理员可能拥有过量可见性；查询和导出按职责分离、短时授权并全审计。
- 删除日志与保留 WORM 证据的义务不同；删除普通日志不能连带删除受保护审计，也不能用 WORM 逃避最小化。
- 前端和移动端错误上报容易绕过服务端脱敏；必须在客户端采集前执行字段白名单。

## 回滚方案

1. 新日志 SDK/序列化器先以 shadow 模式运行，只比较字段集合，不启用新输出。
2. 发现漏记关键排障字段时，通过新增受控结构字段修复，不允许恢复整个请求体。
3. 发现误报时，保留拒绝并进入隔离队列，由隐私/安全人员复核；不能全局关闭检测。
4. 回滚版本必须向后读取上一 schema，并对回滚窗口做字段覆盖、敏感模式和高基数字段检查。
5. 若新平台已写入疑似敏感日志，立即限制访问、计算影响范围、按制度通知并执行受控清理；审计库证据不删除。
6. 恢复门禁：schema 差异为 0、合成 PHI 金丝雀零逃逸、错误路径无请求体、导出审批与审计完整。
