# ADR-014：审计不可篡改——哈希链、WORM、国密签名与第三方校验

## 背景

Atlas 每天目标接收 20 亿条审计事件，审计必须覆盖访问、建议、状态变更、规则/模型发布、签核、破窗、回写和异常。数据库管理员或被攻陷服务不应能无痕改写、删除或重排历史。单一同步全局链可能成为吞吐瓶颈；仅日志文本或仅 WORM 又不能检测内部逻辑顺序篡改。因此采用“确定性分片哈希链 + 周期签名检查点 + WORM 归档 + 第三方独立复算”的组合。

## 选项对比

| 方案 | 篡改检测 | 不可删除 | 吞吐 | 结论 |
|---|---|---|---|---|
| A：应用日志 + 普通对象存储 | 弱 | 弱 | 高 | 拒绝 |
| B：WORM 单目录，不做链/签名 | 文件级较强 | 强 | 高 | 无法证明顺序与跨文件完整，拒绝 |
| C：单数据库链 | 逻辑顺序清晰 | 依赖数据库 | 20 亿/日可能成瓶颈 | 不直接采用 |
| D：分片 SM3 链 + SM2 签名检查点 + WORM + 第三方接口 | 强 | 强 | 可水平扩展 | **采用** |

## 决策

### 1. 审计事件与规范编码

每个事件采用确定性规范编码（字段名排序、UTF-8、整数定长表示、禁止非规范浮点），至少包含：

| 类别 | 必备字段 |
|---|---|
| 身份 | `event_id`、`tenant_id`、`stream_id`、`sequence`、事件发生时间、接收时间、时区/时钟质量 |
| 主体与目的 | actor/服务身份、机构、患者/资源内部标识、what、why/目的码 |
| 决定 | operation、before/after 状态、result、reason_code、政策/规则/模型版本 |
| 完整性 | `prev_hash`、`payload_digest`、`event_hash`、算法标识、签名批次引用 |
| 来源 | traceId、事件生产者、契约版本、数据分类 |

患者姓名、证件号等不直接写入可广泛查询的审计正文；使用受控内部标识，正文只有必要摘要。审计事件一旦接受不可 UPDATE/DELETE，更正用新事件引用原事件。业务写库通过事务 outbox 发送，失败重试使用 `event_id` 幂等去重。

### 2. 分片哈希链

按确定性 `stream_id`（例如租户/审计域/日期/固定分片）分片，确保事件在分片内单序追加；分区规则版本化。每个事件计算：

`event_hash = SM3(CanonicalEncode(event_without_event_hash || prev_hash))`

首事件 `prev_hash` 为流创建时签定的 genesis hash；后续严格引用前一 `sequence + 1` 的 hash。`sequence` 唯一约束和前序检查由审计存储/写入服务强制。分片数、每片目标吞吐和重分片规则由压测决定，为 `[待验证]`。验证方法是以 20 亿/日、峰值和故障恢复流量测分区偏斜、锁竞争、fsync 延迟和尾延迟。

每日/滚动窗口把各流的有序 hash 根、叶数量、序列范围组成 Merkle tree；计算：

`checkpoint_root = MerkleRoot([stream_root_1, ..., stream_root_n])`

用 SM2 私钥对规范化的 checkpoint 生成 CAdES/CMS 或部署批准的签名封装，绑定时间、算法、密钥 ID、证书链、manifest 摘要和用途。签名私钥存于经批准的 HSM/KMS，审计服务只调用签名接口；生产 KMS 对具体国密证书链和证明能力的支持为 `[待验证]`。验证方法是在目标密码模块完成密钥生成、导入/不可导出证明、签名、验签、证书链/吊销和轮换演练。

### 3. WORM 归档

分层设计：在线审计用于近期检索，归档批次写 WORM 对象存储。归档对象名、不可变版本、对象锁合规模式、保留到期权限、删除 deny 列表、独立服务账号和 WORM 回执/对象版本均需验证。普通应用账号、数据库备份和 Atlas 运维账号不得删除/覆盖归档；备份系统也不得恢复成可覆盖原件。

“对象锁/合规模式”的实际语义、底层介质故障和保留期由具体平台保证，附件未证明，均为 `[待验证]`。验证方法：选型时执行写入—尝试覆盖/删除—到期尝试—恢复测试，核对存储端版本/回执和独立控制面权限；不能只以 API 返回码判定 WORM 生效。

归档批次必须含 manifest：事件范围、链根、Merkle 根、签名、WORM 回执和摘要。归档不可用时写入院内加密耐久缓冲；达到安全水位仍无法归档，停止新的非关键发布/扩展并触发 P1，临床救治不得通过无审计路径继续。缓冲同样有哈希链和容量告警，不以内存队列替代持久性。

### 4. 第三方独立校验接口

提供版本化 `verify-audit` API，输入仅含脱敏/哈希材料，不需回传患者正文：

1. 请求携带 manifest、事件或分片摘要、链根、签名、WORM 回执/对象版本和证书链；
2. 第三方重新规范编码、用公开证书验签、检查时间/用途/证书状态；
3. 按 sequence 复算 `prev_hash/event_hash`，检查叶、范围、重复和缺口；
4. 复算 Merkle 根并比较签名内容；
5. 验证 WORM 回执/对象版本和归档清单（能力与证据格式为 `[待验证]`）；
6. 返回逐流结果：OK、MISSING、REORDERED、TAMPERED、UNSIGNED、WORM_UNVERIFIED、CLOCK_OUT_OF_TOLERANCE，并附证据哈希。

接口支持离线文件包和固定版本的 `verify` 工具，第三方不能调用 Atlas 的“自证成功”结果。证书吊销列表离线缓存必须有时间界限；超过界限显示 UNKNOWN，不误报 OK。第三方实现、语言和 WORM 证据适配为 `[待验证]`，通过互操作测试和故障注入验证。

### 5. 监控与告警

每条流监控 sequence 缺口、前序不匹配、签名失败、checkpoint 延迟、WORM 失败、时钟倒退/漂移和分片偏斜。告警事件本身写入另一条受保护审计流。平台所有者不能单方面关闭硬告警；处置需安全负责人和合规负责人双签并全量留痕。

## 可复算推导

每日审计量 2,000,000,000 条，平均每秒：

`2,000,000,000 / 86,400 ≈ 23,148.15 条/秒`

若采用峰值系数 `K=20` 的容量假设，峰值目标约：

`23,148.15 × 20 = 462,963 条/秒`

该 `K=20` 与故障恢复倍数尚未实测，标 `[待验证]`。验证方法：从生产/合成压测提取 5 分钟与 1 小时峰值比，并加入积压重放、WORM 不可用、签名服务降级和节点重启，按最坏组合反推分片数。

若每 60 秒为一批签名，2,000,000,000 条/日对应：

`2,000,000,000 / 1,440 = 1,388,888.9 条/批`

若每 5 分钟一批，则为 `2,000,000,000 / 288 = 6,944,444.4 条/批`。批次大小、签名服务吞吐、树构建 CPU 和尾延迟为 `[待验证]`；验证方法是在目标硬件测 SM3、SM2、Merkle 与 WORM 上传分别耗时，并确保最慢分量有容量余量。

对“任意篡改必检出”的验收定义：选择每个流的任意位置执行覆盖、删除、插入、重排、签名替换、WORM 版本替换各至少 1 次；若流数为 `S`，则 `6S` 个攻击样本，预期 `detected/6S=100%`。攻击生成器、覆盖范围和第三方独立性为 `[待验证]`，验证方法是对外发包执行独立复算、盲化测试和跨实现对拍。

## 安全后果

- 哈希链检测修改/重排，WORM 限制删除/覆盖，签名证明来源，独立校验降低内部共谋信任；四者不能互相替代。
- 分片提高吞吐，但必须防分片边界伪造、漏分片和 checkpoint 不完整；manifest 明确全局集合。
- 审计中仍可能含敏感标识，需独立权限、脱敏和访问告警。
- 强 fail-closed 会增加停用风险；临床紧急处置须走明确、受控且同样留痕的流程。
- 第三方接口泄露 manifest 可能暴露系统活动模式，故只输出脱敏摘要和受限元数据。

## 回滚方案

1. 哈希算法/事件格式升级采用双版本链：新链以旧 checkpoint 摘要为 genesis，在切换点同时签两份检查点；不重写旧链。
2. WORM 供应商不可用时切至经批准的院内 WORM 副本；两者均不可用则停止非关键写入并 P1 告警，耐久缓冲不丢数据。
3. 签名服务异常时保留未签名检查点和告警，恢复后只对已固化 manifest 补签；不得重新解释历史时间。
4. 完整性校验失败立即隔离相关证据、保全快照、轮换/吊销可能泄露的密钥并启动安全事件；不能用“重建链”消除证据。
5. 回滚验收包括旧版本继续验签、链接续、WORM 不可变、第三方离线校验和跨版本清单。
