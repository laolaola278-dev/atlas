## 背景

平台要求同时接入 100,000 台设备、达到 1,000,000 点/秒，并保证告警端到端 P99 小于 1 秒。设备抖动、丢包、探头脱落、重复点和恢复期数据会在数秒内形成连续超阈值；若每个点都直接产生通知，会把网络抖动误报为病情变化并造成告警疲劳。附件同时把时序库选型列为 TDengine/VictoriaMetrics，但未规定原始层、降采样层和告警状态机之间的边界。

本 ADR 只负责“采集、存储、判定、聚合、确认”的技术链路，不替临床负责人批准任何生命体征阈值。所有阈值均须绑定规则版本、适用人群、单位和来源；未取得临床验证材料时标为 `[待验证]`，不得上线拦截。

## 选项对比

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| 仅时序库直写、每点触发 | 实现简单、延迟低 | 网络抖动被放大，重复告警多；峰值写放大 | 不采用 |
| 流处理内无状态阈值比较 | 易于水平扩展 | 难以表达持续时间、恢复迟滞、优先级和人工确认状态 | 不采用 |
| 持久缓冲 + 有状态告警状态机 + 分层时序存储 | 可重放、可审计；能合并抖动；容量与保留策略可分离 | 状态和规则版本必须可追踪；状态迁移测试成本较高 | **采用** |
| 仅从设备侧做去抖 | 节省院内带宽 | 设备型号多、行为不可控；旁路设备或重连时可能漏报 | 不采用 |

## 决策

### 1. 数据路径与存储分层

1. 设备事件先进入院内 Kafka 持久分区，再由 `atlas-monitor` 消费；Kafka 保留期至少覆盖规则计算所需的最大可容忍重放窗口。
2. 原始点在 VictoriaMetrics/TDengine 中按院区、设备内部标识、信号类型和事件时间写入；业务数据库不承载高频原始点。
3. 保存三层视图：短期原始层、分钟级聚合层、长期趋势层。保留天数和压缩率在目标信创硬件上实测后锁定，未实测前标为 `[待验证]`。
4. 每个点携带 `campus_id`、`device_id`、`signal_code`、`event_time`、`ingest_time`、`sequence`、`unit`、`quality` 和 `source_trace_id`；患者关联只在受控查询层完成，设备索引默认不存明文患者标识。
5. 规则计算必须先验证单位、信号质量码和设备校准状态。质量为无效、缺失或探头脱落时，不把“无数据”解释为生理正常。

### 2. 告警状态机

采用 `NORMAL → PENDING → ACTIVE → ACKNOWLEDGED → RESOLVED` 状态，并为设备离线、传感器故障保留旁路状态。

| 机制 | 规则 | 目的 |
|---|---|---|
| 首次超阈值 | 进入 `PENDING`，不立即通知普通用户 | 隔离单点尖峰 |
| 持续超阈值 | 连续 `k` 个合格样本或持续 `T` 后进入 `ACTIVE` | 区分瞬时噪声与持续异常 |
| 恢复迟滞 | 必须低于独立恢复阈值持续 `T_rec` 才解决 | 防止阈值附近反复开关 |
| 告警合并 | 同一患者、规则、优先级在窗口 `W` 内合并为事件，附触发计数和证据区间 | 降低通知数量且不丢计数 |
| 优先级 | 危急值不能被普通队列阻塞；危急阈值需双人批准并绑定来源 | 保护患者安全 |
| 升级 | 未确认超过分级时限则升级到上级岗位；具体时限须临床批准 | 避免无人处理 |
| 确认 | 确认只停止重复通知，不自动关闭异常；关闭需记录处置与证据 | 防止“已读”等同“病情解除” |
| 抑制 | 同一根因可抑制派生告警，但不得抑制原始告警，且父子关系可见 | 控制级联噪声 |

危急规则是否允许单点立即触发、持续时间及恢复阈值均属临床参数，当前均为 `[待验证]`。验证方法是：由急诊、重症、护理和设备工程共同签署参数来源；在历史回放中分别统计危急召回、误报率、通知量与确认时延；设备工程用信号发生器测试探头脱落、网络抖动和校准失效；上线前以影子模式运行并逐例审查差异。

### 3. 去重与重放

- 设备原始事件的幂等键为 `campus_id + device_id + sequence + signal_code`；同一键但内容哈希不同必须隔离并告警，不能覆盖首值。
- 去重窗口至少覆盖设备离线重连、消息最大重试和 Kafka 保留期，三者最大值由实测配置生成。
- 重放不得再次产生对外通知；它只重建时序视图和告警证据，生成 `replay=true` 审计标记。
- 下游只可按事件时间构建视图，但必须同时保留接收时间，以识别迟到数据和时钟偏差。

### 4. 可观测性与安全边界

指标至少包括：接入速率、重复率、无效质量码比例、规则计算延迟、状态转换次数、通知合并比、危急告警确认时延、存储拒绝量、时钟偏差和规则版本。日志不记录患者姓名、证件号、原始报文或设备序列号与患者标识的拼接值。规则、设备映射和去重结果均可按版本回放；任何告警关闭都可追到触发点、通知、确认人与处置记录。

## 可复算推导

### 容量与时延预算

附件给定单实例时序容量假设为 250,000 点/秒，计划 6 个实例：

```text
总毛容量 = 6 × 250,000 = 1,500,000 点/秒
对 1,000,000 点/秒目标的容量系数 = 1,500,000 ÷ 1,000,000 = 1.50
相对 30% 冗余余量 = 1,500,000 × 30% = 450,000 点/秒
```

告警 P99 小于 1 秒采用以下可测预算：

| 环节 | P99 预算 |
|---|---:|
| 接入、校验与鉴权 | 100 ms |
| 持久缓冲与规则计算 | 50 ms |
| 时序写入 | 100 ms |
| 状态机与通知扇出 | 200 ms |
| 传输与时间同步余量 | 50 ms |
| 合计 | 500 ms |
| 指标留余量 | 500 ms |

任何一环节超出预算都必须给出 trace 分位数；合计超过 1,000 ms 即不满足 MP-03。上述 250,000 点/秒和分段延迟是规划假设，均为 `[待验证]`。验证方法是使用 `atlas-loadgen` 纯合成流量持续 30 分钟、72 小时各一轮，记录 ingest 到 notification 的原始直方图，并用目标硬件复测 P50/P95/P99/P99.9 与丢点率；未达到目标不得以平均值代替。

### 合并通知量的解释

设某规则每分钟原始触发 `R=30` 次，持续超阈值合并窗口 `W=5 min`。一个 5 分钟窗口内的**触发数**为：

```text
triggers = R × W = 30 × 5 = 150
```

`triggers` 不是通知数。通知数等于状态机观察到的独立告警 episode 数 `E`：150 次触发可以属于一个持续 episode 而只通知 1 次，也可以分成多个 episode 而产生多次通知；仅凭 `R` 和 `W` 不能唯一推导 `E`。压测报告必须同时记录 `triggers`、`episode_count`、合并比例、通知延迟和证据区间，验证去抖没有删除触发事实。

若额外假设“平均每个 W 窗口 产生一个 episode”，则通知率算例为 `R ÷ W = 6 次/分钟`；该假设、窗口边界和 episode 定义均为 `[待验证]`，不能把 6 次/分钟当作生产承诺。

## 安全后果

| 影响 | 后果 | 控制与剩余风险 |
|---|---|---|
| 漏报 | 危急异常未通知 | 危急规则单独高优先级队列、断连检测、端到端合成告警测试；误/漏报平衡仍需临床验证 |
| 误报 | 告警疲劳、注意力被稀释 | 持续时间、迟滞、合并、影子模式；参数不自动学习更新 |
| 重放重复通知 | 重复处置或错误升级 | 幂等键、状态版本号、重放隔离标记 |
| 错误患者/设备关联 | 对错误对象告警 | 设备到就诊上下文短租约、双人核对、关联变更审计 |
| 数据越权 | 通过设备接口识别患者 | 租户隔离、最小字段、ABAC、全访问审计 |
| 数据洪水 | 告警队列被压垮 | 每院区/设备/规则令牌桶、硬配额、危急通道保留容量 |

未完成的临床参数验证是上线阻断项；不能以“去抖减少消息”证明临床安全。

## 回滚方案

1. 发布前保留旧规则引擎和新规则的版本化并行开关；默认影子模式，不产生通知。
2. 回滚时将 `alert_policy_version` 原子切回上一已验证版本，停止新状态机消费并从 Kafka 偏移重放；重放只更新证据，不重复通知。
3. 若新存储影响急诊链路，在 5 分钟内把写入切回上一兼容适配器，保留 Kafka 中的原始数据；不得用丢弃数据换取恢复。
4. 保留 `PENDING/ACTIVE/ACKNOWLEDGED` 状态快照。回滚后按原事件时间恢复，冲突状态进入隔离队列并由值班工程师与临床负责人共同处置。
5. 验证条件：回滚后 15 分钟内恢复基线 P99、告警计数与输入计数可对账、时序数据无新增缺口；未满足时回滚“性能隔离”策略而非关闭危急告警。
6. 任何规则回滚均生成审计事件；不得删除失败版本及触发数据，便于根因分析和监管检查。
