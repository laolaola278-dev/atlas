## 背景

附件给出的“两库”规模是 88 类规则、24.7 万知识点，但未附正式数据结构、发布周期、来源许可和版本差异。Atlas 需要把这些知识组织成可编译、可测试、可按生效时间解释的规则资产，而不是把大规模条目硬编码或仅放入向量库做语义检索。医保限制涉及适应症、限儿童、限性别、限频次等，错误命中可能造成不合规服务建议或费用争议。

## 选项对比

| 方案 | 结构化查询 | 版本追溯 | 复杂条件表达 | 结论 |
|---|---|---|---|---|
| A：仅知识图谱/向量检索 | 弱 | 可做 | 条件语义不稳定 | 拒绝作为裁决 |
| B：24.7 万条全部硬编码 | 可查 | 差 | 难维护 | 拒绝 |
| C：知识点库 + 可编译规则库 + 物化索引 | 强 | 完整 | 可测试 | **采用** |

## 决策

### 1. 两库职责

| 库 | 内容 | 规范标识 | 可否直接裁决 |
|---|---|---|---|
| 知识点库 KP | 药品/项目/人群/地域/支付条件等原子事实及引用 | `kp_id + version + effective_at` | 否，须被规则引用 |
| 规则库 RT | 条件、计算、结论、例外、证据与风险等级 | `rule_id + version + effective_at` | 由确定性引擎求值 |

知识点不是自然语言段落。每条至少含：稳定 ID、类别、规范化值、代码系统、来源页/节、原文摘要、内容摘要、适用地区/人群、生效/失效时间、来源版本、审批状态和修订关系。规则通过不可变 `kp_ref` 引用知识点，禁止复制后各自漂移。

附件所述 88 类和 24.7 万条为输入规模，真实条目数、类别粒度、增量频率及覆盖完整性为 `[待验证]`。验证方法是取得有授权的数据包与发布说明，计算逐类数量、重复率、空字段、孤立知识点、悬空引用和版本缺口；由医保业务人员抽样核对。

### 2. 分类、编码与派生

88 类作为顶层分类，但分类版本可演进。每个知识点有多标签时保存“主类+附加类”，唯一主类计数满足：

`Σ count_primary(c) = N_unique_kp`

若给定 247,000 个唯一知识点、88 个顶层类，则平均每类为：

`247,000 / 88 = 2,806.818…`

约 2,807 条/类，仅用于容量基线，不能强制各均分。展示类树与规则实际分类分别统计；`247,000` 是否唯一、是否存在多标签为 `[待验证]`。

### 3. 版本与生效模型

| 字段 | 作用 |
|---|---|
| `version_id` | 不可变内容版本 |
| `supersedes` | 指向前一版本或替代映射 |
| `effective_from/to` | 业务生效区间 |
| `received_at` | 系统收到时间，不冒充生效时间 |
| `approval_id` | 来源/业务/合规审批链 |
| `content_digest` | 对规范化字节计算的内容摘要 |
| `validation_run_id` | 回归、对拍、发布门禁记录 |

发布日期、收件日期和生效日期分开。回放历史案件时按事件发生时间选择当时活动版本；不得用今天规则重写过去结论。紧急更正也发布新版本并标注影响范围，不覆盖旧包。

规则编译输出为带内容摘要的不可变 bundle：

`bundle_digest = H(canonical(kp_bundle) || canonical(rt_bundle) || compiler_version || schema_version)`

运行记录保存 `bundle_digest`、规则命中、输入事实引用和解释节点。知识库发布后先执行全量差异清单、属性测试、对拍和抽样业务复核，再原子切换活动指针。

### 4. 查询和执行

确定性编译器将规则 DSL/Rego 编译为可验证 AST/程序；常用查询物化到列式索引，不能物化无法失效的个性化结论。复杂组合允许并行求值，但最终按生效版本、安全级别和稳定 `rule_id` 排序，不能用搜索相似度改变裁决。

冲突处理：同时保留独立命中；同等级矛盾升级人工；缺失地域/人群/有效期返回 `INDETERMINATE`；规则引用已过期知识点则规则不可用并告警。向量检索只用于帮助人员查找来源，不参与金额、资格或限制结论。

### 5. 审计与质量

每次命中记录 `rule_id/version`、`kp_id/version`、输入字段、执行时间、结果和证据；规则更新产生可读差异和影响分析。质量指标至少包括：无引用率、悬空引用率、重复语义率、无测试规则率、版本回放一致率、冲突率、人工推翻率。源文件与编译产物都不可变，发布包签名并记录审批。

## 可复算推导

设数据源有 `N_raw=247,000` 行，规范去重后 `N_unique`，重复率：

`duplicate_rate = (N_raw - N_unique) / N_raw`

若验证得到 `N_unique=245,000`，则：

`(247,000 - 245,000) / 247,000 = 2,000 / 247,000 ≈ 0.00810 = 0.81%`

这 0.81% 只是算例，不代表附件数据质量；`N_unique` 为 `[待验证]`。验证方法是对内容摘要、来源标识和语义等价三层分别去重，并由业务抽样仲裁，报告重复原因。

全量回归的最小工作量为：

`N_test_scenarios ≥ N_rules × 2 + N_version_boundaries + N_conflict_cases`

例如 4,000 条规则、8 个生效边界和 200 个冲突案例，则至少：

`4,000×2 + 8 + 200 = 8,208` 个场景。还需每个临床类别分层抽样，场景总量不能用总数掩盖覆盖缺口。规则数与案例库规模为 `[待验证]`，以编译器清单和风险评审结果计算。

## 安全后果

- 确定性规则提高可追溯性，但源数据错误会规模化传播；每次发布必须全量回归和人工抽样。
- 知识库不直接裁决可防止语义检索幻觉进入费用/资格判断。
- 双重版本与生效时间增加存储运维，却能保留历史责任依据。
- 地区/医院差异若未显式建模，可能跨地域错用；默认不匹配即拒绝。

## 回滚方案

1. 新 bundle 发布异常时，原子回切上一签名 bundle；未决运行保留原版本结果。
2. 源数据回滚采用撤回发布并追加修复版本，不重写历史包。
3. 编译失败时保持上一活动指针；禁止运行半编译规则。
4. 回滚验收包括内容摘要一致、全量回归差异为零、历史时间点重放一致、影响分析覆盖和审计可追责。
