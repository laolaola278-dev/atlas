# ADR-004：FHIR R4 资源建模范围与本地扩展策略

## 背景

Atlas 接收院内 HL7 v2、FHIR、数据库视图和设备数据，并向 EMR/CPOE 提供结构化协作结果。若各服务直接保存松散 JSON 而没有统一 R4 Profile、扩展命名和术语绑定，同一检验值、药物编码或临床状态会因院区解释不同而产生安全歧义。FHIR R4 生态成熟，但生产性能、版本一致性和本地术语仍需自研校验层。

## 选项对比

| 方案 | 互操作性 | 本地表达能力 | 验证成本 | 结论 |
|---|---|---|---|---|
| A：原样存储 FHIR R4 JSON | 高 | 低 | 最低 | 无法保证语义一致，拒绝 |
| B：全部映射为内部简化模型 | 初期可控 | 较高 | 映射和丢失分析成本高 | 拒绝作为交换契约 |
| C：R4 基础资源 + Atlas Profile/Extension + 术语绑定 | 高 | 高且可审计 | 可按资源分阶段自动化 | **采用** |

## 决策

### 1. 首期资源范围

首期交换契约采用 FHIR R4，以下资源为强制建模对象：

| 临床域 | R4 资源 | Atlas 约束重点 |
|---|---|---|
| 身份与就诊 | `Patient`、`Encounter`、`Practitioner`、`Organization` | EMPI 引用、院区命名空间、机构标识 |
| 临床事实 | `Condition`、`Observation`、`AllergyIntolerance`、`Medication`、`MedicationRequest` | 临床状态、证据、术语、版本 |
| 诊断与报告 | `DiagnosticReport`、`DocumentReference`、`ImagingStudy` | 报告状态、文档安全标签、DICOM 元数据引用 |
| 协作 | `CarePlan`、`Task`、`Consent`、`Provenance` | 责任人、期限、授权来源、审计链 |
| 建议 | `ClinicalImpression` 仅作容器，不作为自动诊断 | Atlas 建议扩展必须显式 `isSuggestion=true` |

超出范围的资源可以保存为原始消息，但不得直接进入临床写路径；新增资源必须经数据治理、临床语义和兼容性评审。实际院内字段覆盖率与资源优先级为 `[待验证]`。验证方法是抽样最近一个完整统计周期的接口流量并形成“资源—字段出现率—消费方”矩阵，任何计划外临床字段进入变更评审。

### 2. Profile 与 Extension 原则

- 基础类型保持 R4，不通过修改基础字段含义来适配院区差异。
- 必填差异、值集和基数约束写入命名 Profile；跨资源约束优先用 `Constraint`。
- 本地确有信息但标准元素不能表达时，使用 Extension；命名遵循 `atlas-organization` canonical 前缀，核心 URL 与发布值均为 `[待验证]`。验证方式是建立 canonical 域名、命名空间审批、发布签名和 HAPI/官方 Validator 互操作测试。
- 禁止在 `display` 中编码机器语义；标准 code 不可表达时必须增加明确 code system 与版本。
- 未知扩展必须被接收方安全忽略或返回受控错误，不得丢弃后继续临床写入。
- 每个 Profile 发布包必须含 JSON、结构定义、示例、搜索参数说明、变更日志和验证报告。

### 3. 术语服务与版本管理

| 术语 | 用途 | Atlas 要求 |
|---|---|---|
| LOINC | 检验/测量编码 | 代码、系统、版本、显示名共同记录 |
| SNOMED CT | 临床概念、问题/身体结构等 | 仅在许可和部署地域允许范围内使用；替代/映射关系版本化 |
| ICD-10 / ICD-11 | 诊断与分组上下文 | 不把分组结果反写成诊断事实 |
| ATC | 药物分类辅助 | 不替代院内药品主数据和药物规则引擎 |

资源内保存 `system|code`，引用服务保存 `system|code|version`。同一标识在版本迁移时不得原地改义：发布新版本、建立显式替换/映射、保留旧版本读取和按生效时间解析。发布状态为 `draft→reviewed→approved→published→deprecated/retired`；已发布版本不可编辑。

SNOMED CT、LOINC 等具体许可、再分发及本地化约束是 `[待验证]`。验证方法：由法务/采购核对部署地域和实际使用模块的许可证、证书及数据再分发条款，保存书面结论；技术验收执行版本装载、查询、映射、升级与回滚测试。

### 4. 校验分层

| 层 | 时机 | 失败策略 |
|---|---|---|
| 词法/结构 | 接入时 | 隔离消息，不生成临床建议 |
| Profile 语义 | 入库与发布前 | 拒绝资源或进入受控修复队列 |
| 术语绑定 | 入库/查询时 | 必需 code 不可解析则阻断；可展示项按策略降级 |
| 参考实现对拍 | CI/发布门禁 | 官方 Validator 与 HAPI 结果差异未解释则失败 |
| 本地性能层 | 预生产压测 | 不得放宽语义校验；仅可缓存结果 |

## 可复算推导

首期 17 个资源分别需要“基础 Profile、扩展清单、术语绑定、2 个示例、校验测试、兼容测试”6 类制品：

`17 × 6 = 102` 个版本化制品。

每次破坏性变更至少复验 6 类制品，17 个资源全量复验为 `17 × 6 = 102` 项；若每次 2 个并行校验槽、平均每项 3 分钟，则 `102 × 3 / 2 = 153 分钟`。这些是规划容量公式，不是实测时长；并行度和单项目耗时为 `[待验证]`。验证方法是在目标 CI 环境对同一版本运行至少 10 次，报告中位数、P95、失败率和缓存命中前后的差异，并据安全余量配置门禁。

## 安全后果

- 统一 Profile 降低跨院区语义漂移，但错误 Profile 会系统性传播错误；所有发布必须经过临床与互操作双签。
- Extension 保持标准兼容，也可能造成接收方静默忽略；高风险扩展必须 `must-support` 或触发受控阻断。
- 术语版本固定使历史证据可重放；代价是存储和映射运维复杂度增加。
- 原始消息、Profile、术语和实际校验器版本必须同时进入证据链，禁止用当前术语重写历史显示。

## 回滚方案

1. Profile 与应用代码分别采用双版本并存；先回滚消费者，再回滚生产者，不回滚已发布术语含义。
2. 术语导入失败时固定到上一完整快照；回放产生新发布版本，不修改旧版本。
3. 校验规则过严导致临床消息被拒时，可进入隔离队列并建立受控兼容 Profile；不得直接关闭校验。
4. 回滚验收包括官方 Validator、历史资源重放、跨版本映射、未知扩展处理和错误码稳定性。

## 待验证清单

| 标记项 | 验证方法 | 通过证据 |
|---|---|---|
| `[待验证]` 首期资源与字段覆盖 | 周期流量抽样、临床消费方矩阵 | 覆盖报告与审批记录 |
| `[待验证]` Atlas canonical 前缀和签名发布 | 命名空间、域名、证书与官方校验器联测 | 发布清单与验证报告 |
| `[待验证]` 各术语许可与再分发条件 | 法务/采购书面核对，版本化装载测试 | 许可证意见与导入报告 |
| `[待验证]` CI 校验容量算例 | 目标环境至少 10 次基准运行 | 耗时分布和容量报告 |
