# ADR-011：DRG/DIP 分组器集成与本地化差异

## 背景

DRG/DIP 分组结果依赖病案首页诊断、操作、费用、年龄、性别、出院状态、规则版本及地区口径。Atlas 可辅助准备数据和给出候选分组，但不能自行确认结算，也不能用 LLM 推断缺失字段。集成必须保证同一输入和版本产生可复算结果，并让院区本地化差异可追踪，而不是散落在代码分支中。

## 选项对比

| 方案 | 结果一致性 | 数据边界 | 升级治理 | 结论 |
|---|---|---|---|---|
| A：LLM 直接分组 | 不可重复 | 可内嵌但无保证 | 难以验证 | 拒绝 |
| B：分组逻辑全部手写重实现 | 可控 | 本地 | 规则复杂且易偏差 | 拒绝 |
| C：经批准的官方/授权实现作为隔离引擎，Atlas 管契约、差异和审计 | 可复算 | 数据可留院 | 版本化适配 | **采用** |

## 决策

### 1. 分组器边界

分组器只接收完成隐私最小化、术语规范化和质量检查的病例快照；输出候选 DRG/DIP 组、规则追踪、所需字段、冲突和解释，不直接发起结算。Atlas 通过版本化适配器调用；LLM 只可对已输出的追踪生成草稿摘要，不能参与分组计算或补齐字段。

优先使用经批准、许可允许在目标部署地域运行且支持确定性和版本标识的实现。具体产品、授权模式、执行方式及对本地化配置的开放程度为 `[待验证]`。验证方法：采购/法务核对许可与部署权；使用官方或经认可的黄金数据集对拍；重复输入 100 次结果摘要应一致，并把运行环境、容器摘要和配置摘要纳入证据。

### 2. 不可变输入契约

`GroupingCase` 至少包含：病例稳定标识哈希、院区、数据期间、DRG/DIP 体系、年龄/性别等必需人口学字段、诊断与操作术语、费用明细、缺失/冲突清单、临床签核状态、源数据版本、分组器版本和本地差异包版本。临床事实仍来自 FHIR/规范 HL7，费用字段通过受控映射进入，不能让分组器从任意 SQL 自由读取。

每次计算记录：

`grouping_run_id = H(canonical_input || engine_version || rules_version || local_profile_version || runtime_image_digest)`

任何输入、引擎、规则或本地配置变化均形成新 run。相同摘要才可复用缓存；缓存不得替代历史运行记录。

### 3. 本地化差异

| 差异层 | 示例 | 处理 |
|---|---|---|
| 体系/版本 | DRG 或 DIP、版本/年度 | 明确选择，禁止混合 |
| 地区/支付口径 | 地区政策、病例组合口径 | 仅加载经批准且签名的 profile |
| 字段映射 | 本地诊断、操作、费用代码 | 版本化映射与冲突报告 |
| 权重/阈值 | 机构获准配置的参数 | 参数文件签名、生效日期、限权 |
| 医院流程 | 病案首页签核与仲裁 | 人工复核，不改底层分组结果 |

本地 profile 不允许覆盖引擎核心计算；若授权引擎不支持受审计的本地化，则 Atlas 只做映射和结果标注，不“修补”结果。规则差异、来源、审批、生效区间和影响病例均可导出。

### 4. 缺失、冲突与复核

必需字段缺失或代码映射冲突时返回 `INDETERMINATE` 并列出修复项；不得以常见值填补。候选结果可进入病案/医保人员审核台，但任何提交、支付申请或正式编码确认遵循 ADR-001 的签核和不可变证据链。人工修改记录原候选、修改字段、理由、审核者和最终决定，不覆盖引擎输出。

每次规则/引擎升级执行：历史病例重放、黄金集对拍、本地差异影响分析、人工盲审和分地区回归。差异率超过批准阈值时禁止发布；阈值由业务和合规确定并标 `[待验证]`，验证方法是从历史回放建立基线并用序贯试验评估可接受差异。

### 5. 运行隔离与数据最小化

分组器可作为院内独立进程/容器或授权本地进程运行，不得默认调用互联网服务。若候选远程服务确有必要，须完成数据不出院、个人信息处理、合同、跨境/出域和密钥专项评审。当前采用“本地隔离适配器”为基线；例外能力为 `[待验证]`，验证方法是法务/安全出具书面允许并经 `atlas-privacy` 数据流门禁批准。

## 可复算推导

复现判定：设两次运行的规范输入摘要 `H_in`、引擎摘要 `H_engine`、规则摘要 `H_rules`、本地 profile 摘要 `H_local`、镜像摘要 `H_image` 相同，则预期 `run_id` 相同；任一项变化则应产生新 run。若黄金集 `N_g` 中有 `d` 个结果差异：

`difference_rate = d / N_g`

若 `N_g=2,000、d=4`，则 `4/2,000=0.002=0.2%`。是否能接受 0.2% 及黄金集构成、授权对拍口径尚未确认，均为 `[待验证]`。验证方法是由支付规则专家预先批准分层黄金集和阈值，使用 McNemar 置信区间及按版本/地区分层结果，而非只看总体点值。

批量处理吞吐：

`cases_per_second = case_count / elapsed_seconds`

例如 200,000 例、3,600 秒，平均为 `55.56 例/秒`；尾延迟、病例复杂度分布和引擎资源占用为 `[待验证]`，必须在目标硬件用代表性复杂度分层测量。

## 安全后果

- 授权引擎降低自行重实现规则偏差，但带来供应商、许可和升级依赖。
- 不确定性显式返回可能降低自动化完成率，却避免用 LLM 或默认费用填补造成错误分组。
- 本地化配置可适配医院实际，但若无签名和生效区间会形成不可见分叉。
- 候选分组绝不等于正式支付或临床决定，必须保留人工责任边界。

## 回滚方案

1. 新引擎或规则发布失败时原子切回上一签名版本，缓存按摘要自动失效。
2. 本地 profile 异常时停用该 profile，使用上一批准版本或返回需人工处理，不回退到未治理默认值。
3. 远程例外路径异常时回到院内隔离执行；无法分组则阻断正式流程但保留原始病例。
4. 回滚验收包括相同输入同 run 复现、黄金集一致、历史输入按原版本重放、本地差异可解释和人工修改全量有审计。
